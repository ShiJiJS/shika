# 建库准备与列表加载修正

2026-10-17，基于 NAS 首次大库测试反馈调整 V1；范围仍为用户已确认的 B 风格和真实服务客户端。[V1 #23](https://github.com/ShiJiJS/video_viewer/issues/23) 保持开放，目标手机与性能测量继续记录。

## 行为与边界

- 首次建库、追加未准备目录和恢复后核对期间锁定预览；已完成的普通库做增量扫描时保持可用。每条扫描结果仍逐个提交，不因客户端关闭或容器重建全部重来。
- 准备状态由服务端提供，读取进度不触发重新扫描。目录完成时间在完整遍历和身份核对之后保存；阶段、处理/发现数、文件字节量、失败/暂缓与逐目录状态持续落盘并自动同步。
- 准备中轮次不暴露部分候选为完整库；完成后补全不完整候选。已有完整轮次保持顺序与位置，历史回收条目不导致错误重排。日常扫描新增内容仍留到新轮次。
- 接近视频库底部自动加载下一页，使用跨两列的紧凑旋转反馈。分页不重复提交，失败保留卡片与位置，在原处重试相同偏移。进度更新独立于媒体列表发布。
- 播放初始化等待改为前台 30 秒、相邻准备 20 秒；超时、临时连接/来源错误最多自动重试一次，先释放旧播放器并检查页面仍有效。最终失败保留手动重试/滑走入口。这是对临时失败的恢复措施，没有把用户手机上的所有播放失败归因于扫描或网络。
- 原文件、扫描身份、标签、回收记录和任务仍由服务端持久管理。镜像升级保持管理数据与原媒体挂载，口令与 App 加密凭据不随打包重置；不对个人收藏执行故障、试删或恢复测试。

## 验证

服务端：完整 pytest 83 项通过（77.35 秒）、Ruff 通过。新增/更新测试覆盖处理过程中可读且持续保存的统计、初扫播放锁、重启后续扫、完整候选生成、普通增量不锁、恢复轮次含历史回收项，以及重开后扫描身份/标签/回收索引保留。真实 HTTP 背压测试改为等待权威准备状态，避免把首条入库当作全库就绪。

Flutter：57 项单元/界面测试通过，覆盖准备时无播放器、进度变化不重载列表、自动分页与失败原偏移重试，以及后台扫描结束后清理外部改名目录缓存。静态分析通过。

Android 16 / API 36 / x86_64 软件渲染模拟器：使用固定 8761 可丢弃生成素材实例，检查准备页、媒体目录状态、自动解锁、27 条完整轮次、自动加载第二页且只请求一次；注入连续四次 HTTP 503 后实际播放器恢复初始化。实际截图查看了准备态与整行加载动效。复现：

```powershell
python scripts/run-client-connection-test.py --preparation
```

另重新执行 I6 三个 Android 进程：备份、回滚、中断恢复、空实例映射和再次重开均通过，轮次/位置、标签/回收与实际媒体文件保留。恢复后先等待目录核对，再比较可播放轮次，不能在准备阶段断言播放已就绪。

新流程开发中通过一次，最终版本再连续通过两次（29 秒、31 秒）。中间有一次因另一个测试提前重置共享夹具而中断，未当作产品成功证据；后续改为串行运行。实际查看的 [准备状态截图](integration-evidence/library-preparing.png) 和 [分页加载截图](integration-evidence/library-loading-more.png) 保留了已选 B 风格，未出现文字溢出或缩略图加载错误。使用生成花卉素材，图像不含个人 NAS 内容。

原始日志、脱敏 HTTP 轨迹和模拟器截图保存在忽略目录 `tmp/client-e2e`；不要同时运行两个会重置 8761 实例的原生测试。目标 NAS/Find X8 的实际播放问题和性能仍需新包继续验证，模拟器结果不替代目标硬件验收。
