# 大批量图包删除清单：等待、进度与续查

对应 [#184](https://github.com/ShiJiJS/shika/issues/184)。本次只修复已交付功能，不恢复其他暂停中的开发和验收。

## 问题与结果

用户选择数百个图包后，尚未确认永久删除便出现连接超时。服务端已受理的清单仍在后台逐图核对；真实已有任务的只读记录表明，这种规模可能需要二十多分钟。旧客户端每轮最多等待25秒，网络读取超时后直接显示错误，“重新准备”又会增加一份重复核对任务。

现在弹窗持续查询原清单，显示已核对图包数、当前已核对图片数及排队/核对状态。正常查询间隔2秒，短暂网络超时、网络不可用、408/429/5xx后每5秒继续读取原结果。每次HTTP仍有既有超时限制，整个准备过程不再被25秒截断；没有通过无限延长单次HTTP来掩盖断线。准备请求响应丢失后只GET原请求，不自动重复POST。

已有“保存的删除选择”中，在准备POST之前持久保存当前最多1000个图包的准备请求编号和对应ID。关闭、重开、重新创建读取器会先查同一编号；明确重新准备时先保存新编号。批次范围变化、历史选择或并发更新不能沿用错误编号。新增字段兼容没有此字段的旧记录。这个编号只是只读准备请求，不是永久删除授权。

准备过程中隐藏“重新准备”；完成且有效、范围和摘要均匹配后，才允许用户重新勾选确认。原文件指纹、清单过期、连接/管理数据变化、持久命令日志和真正删除前的校验保持原逻辑。关闭弹窗会取消查询和等待计时器，迟到结果不能授权或触发删除；服务器已受理的只读核对不因关闭而自动取消。

## 范围与验证

- 仅移动端变更，NAS服务仍为preview.8，无服务端迁移或重启。
- 真实NAS只读取已有准备任务状态；没有创建新的真实删除任务，没有执行恢复或永久删除，没有修改用户原图片。
- 回归用内存模拟服务和本机HTTP夹具；真实超过26秒的等待检查覆盖原25秒窗口，另外覆盖响应丢失、短暂超时、关闭、622项进度、普通/2倍字体、保存及重新准备后的续查。
- 其他回归涵盖图包回收、选择持久化、操作日志、删除历史、任务入口和布局；最终结果见[第32版交付说明](../../nas-app-preview-2026-11-02-code32.md)。没有把旧的全套或实体手机检查算作本次通过。
- 用户另行要求保留的回收站记录在私有`backups/`和NAS副本中，继续保留、不入GitHub、不当作临时文件清理。原型继续独立于App打包目录。

## 使用边界

本次改变等待和反馈，不加速数万张原图的内容核对，也不免除确认。旧版已经排队的准备任务继续存在；新版无法从旧版未保存的随机编号中恢复身份，但新版开始保存的当前批次可持续续查，避免此后反复新增。
