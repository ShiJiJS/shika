# LF7 整份图包恢复计划

问题：旧 `PackTrashSession.restoreSelected` 在 App 内每1000项循环提交，离页会停止后续批次，关闭后完整选择也无法找回。最终行为必须是一次确认整份逻辑恢复，由服务端持续推进；重开仅查询原计划。

## 持久边界

新增0012迁移：`pack_restore_plans` 保存父Task、原请求指纹、历史/停止标记和固定批次大小；`pack_restore_members` 保存完整且不可变的有序选择、包/回收身份、名称/路径及接入根/代次/内容版本；`pack_restore_batches` 为每个有界区间唯一绑定既有PackFileOperation。

每份1–50000项，去重排序后计算请求指纹。同请求同成员返回原计划，不再入队；异成员冲突。完整成员先在一个事务落库，缺失/跨类型使整个接收回滚。接收只选标量，不载入每包图片清单；数据库参数按500项分段，批量插入成员。已知忙碌/过期项保留为失败成员，不偷偷换身份。

计划成员与既有待核对文件步骤共同持有包级预约。扫描、普通恢复/整理、永久删除清单及重试都经过同一预约查询；尚未生成子批次的成员也受保护。

## 后台与恢复

后台单工作器按最多1000项建立子操作，子操作、步骤与父计划链接在一个事务提交。复用原逻辑恢复引擎和CAS校验，不增加移动文件/递归删除路径。父结果只保存标量计数，成员另行分页；任务列表显示父计划，子操作仍可按ID审计。

每轮先找已受理的最新子批次：未结束或需要核对则先恢复同一操作；已结束先把逐项真实结果计入父成员，然后才考虑下一批。已知失败保留并继续其它成员，不自动重试失败项。成功步骤不会重复恢复，包代次只增加一次。PackOperations启动不再单独调度计划子操作，避免父子队列重复运行。历史父计划不恢复，历史子操作不执行。

停止是显式写命令：先持久标记，当前已受理批次仍核对至真实终态，未开始成员才标为stopped并释放预约。`processed`仅包含真实成功/失败；`stopped`另计，不伪装成功或失败。全部结果已结束时停止不改写完成时间/阶段；重复停止请求不重新入队。服务关闭在批次边界保留interrupted，重启继续原计划。

扫描并发也属于此契约：扫描在开始时保存可处理图包的身份/代次，读取及发布时发现新恢复或代次变化就跳过该身份，最终只能把起点快照内仍未变化的成员判缺失。否则启动扫描可能把已恢复目录重新导入，或在预约释放后把之前跳过的图包判缺失。两个固定交错测试分别在首次处理目录前和最终缺失核对前完成恢复，验证原ID、代次和可用状态均保持；强杀测试还等待启动扫描结束再验收，不能拿中间staging记录证明最终身份。

## 接口

| 接口 | 契约 |
| --- | --- |
| POST `/api/v1/pack-restore-plans` | request_id + 完整trash_ids；202返回已持久父计划 |
| GET `/api/v1/pack-restore-requests/{request_id}` | 只查原回执，404不提交 |
| GET `/api/v1/pack-restore-plans/{id}` | 标量进度、停止/历史标志及固定batch_size |
| POST `/api/v1/pack-restore-plans/{id}/stop` | 幂等显式停止后续批次；历史计划拒绝 |
| GET `/api/v1/maintenance-tasks/{id}/items` | 原成员分页，unfinished包含失败、未开始及已停止；不靠App当前列表估算 |

服务端能力 `pack_restore_plans`。既有每次最多1000项恢复协议保留兼容；它不是新App最终整份恢复流程。计划子批次拒绝从普通重试API重放，失败后需要用户核对并明确重新选择建立新计划。

## 实施状态与剩余工作

服务端阶段见#42；App已由#43接入整份计划、受保护的原请求记录、只读核对和停止。具体实现及真实安全存储强停三轮见 [App设计](LF7-RESTORE-CLIENT-DESIGN.md)、[LF7记录](LF7.md)；不能用这一条路径替代完整LF6/LF7/LF8验收。

App接线要求：使用现有安全存储适配器和明确版本的新记录键，在首次POST前保存同一连接/实例的request ID、完整确认成员及指纹；保存失败不提交。已知plan ID绑定原记录，未知响应重开只GET原request，不重发POST。受理整份计划后解除页面等待，不再由Widget生命周期控制服务器；任务详情分页读取原成员，停止按钮另有持久化请求与确认，旧连接/数据代次的迟到结果不得改当前状态。设置待核对提示和回收站都能找到原计划；不要要求用户重新选一遍才能核对。

客户端必须覆盖取消/写盘失败/响应丢失/404/换连接/迟到结果，原生需实际使用SecureStorage强杀重开，并核对整份父计划、子批次唯一性和所有源文件哈希；不能继续用内存仓库声称进程持久已通过。

物理永久删除仍逐批精确清单与明确确认，绝不能自动处理未经确认的下一批。永久删除剩余选择的持久化另需继续；完整备份v2必须纳入父/子/成员并历史化，当前受保护v1会拒绝省略这些新数据。真实SecureStorage强杀、完整设置/默认值迁移、LF8所有原型/真机NAS仍未完成。冻结原型独立且不修改。
