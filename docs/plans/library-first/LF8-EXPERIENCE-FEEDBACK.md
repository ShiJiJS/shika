## 核对结论

1. 客户端和服务端的阅读默认均为横向。NAS只读核对尚未保存reader_defaults，因此也走横向兜底。现有偏好模型支持单图包覆盖和继承默认，可以在保留个人选择的前提下改变默认。
2. 扫描本来是一轮任务串行处理视频再图包，客户端准备卡还主要读取视频的progress/counts，未完整解析图包类型进度及pack_*阶段。服务端图包根明细也不够：本次观察整体处理786张/11包，根条目却仍是discovering、已发现0/处理11。这是数据与展示两层缺口。
3. 旧浏览页没有彻底删除，用于旧服务兼容。新版管理页也复用了legacyBuild；其中仍有go('browse')、多层PopScope及失活保留页面。新服务出现旧页有可疑代码路径，但手机这次偶发的唯一触发顺序尚未复现，不能声称已定位根因。
4. 客户端和服务端共28行可展示文字使用了用户不希望的措辞，包含菜单、提示、标签编辑和错误；应该统一处理，操作对象/确认/请求/撤销规则不变。
5. 横向阅读有1–4倍缩放，纵向分支只有滚动列表和单击，确实未接入缩放。应在纵向连续画面直接缩放并继续移动，保留续读锚点与延迟加载。

这里只读访问NAS所属容器内数据库，使用mode=ro。未写入默认设置、未重启/触发扫描、未读取收藏名称或图片。用户对首次体验的反馈是缺陷/需求证据，源码核对不替代真机复现。

## 确定的操作规则

- 默认纵向仅作为默认值；已单独保存的图包方式优先，不批量覆盖个人选择。已有进度但无独立偏好的图包仍继承默认，页码与页内位置保留。
- 扫描以“设置中接入的媒体目录”为独立单位。视频目录V、图包目录A/B各自有阶段、数字和结果；A完成后B仍运行时保留A的完成记录。目录内的几百个图包不变成几百张源目录卡片。
- 独立进度不等于多个并发扫描器。继续控制NAS负载；全部扫描与指定目录重扫都经同一调度排队，不触及其它根的状态/身份。未知最终总量时显示已发现数，明确视频/图包/图片单位。
- 新服务只走四个主入口和明确的管理/内容返回关系；兼容旧服务的旧界面单独隔离。不能用破坏旧服务兼容的方式遮住返回问题。
- 操作文案使用“移入回收站”“标签”“撤销移除”等自然表达；永久删除等关键信息保留，不引入单张图片操作，不改变文件管理边界。
- 纵向缩放拟沿用1–4倍、双击2倍/复位；放大后可左右查看、继续上下阅读。返回先复位缩放，续读记录仍基于稳定页ID/页内位置；缩放比例不默认写入云端。

## 实施顺序和交付检查

1. 优先复现/修复新版返回露出旧页；默认纵向和文案可作为同一体验补丁中的独立事项推进。
2. 完成目录进度契约、持久化和指定目录排队，再接扫描页面。V+A+B、离线/停用/部分失败/重启和重叠根归属用可丢弃样本核对。
3. 实现纵向缩放。重点检查双指与单指交接、深位置/窗口补页、真实旋转、复位/返回、坏图和缓存上限，再补目标手机体验；不复用横向旧证据当纵向已验。
4. 每次实际交付都记录对应源码、服务兼容能力和同版原签名APK，保持递增内部号与配套回退包。NAS升级先备份，用户真实收藏不用于删除测试；本次规划不交付新包。
