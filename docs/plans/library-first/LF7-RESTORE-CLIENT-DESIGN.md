# LF7 整份恢复：App 接线

回收站的“恢复”对支持 `pack_restore_plans` 的服务改为一次确认完整选择，最多50000包。App只提交父计划，受理后立即解除页面等待；离页或关闭不会控制服务端的后续批次。旧服务保留原每批协议作为兼容路径，不能把它当作当前服务的最终整份恢复实现。

## 模块与记录

`PackRestorePlans`封装提交、原恢复/停止回执GET、已知计划读取与本机结算；不在页面轮询或生成子批次。不可变`RestorePlanCommand`保存明确动作、原request ID、完整目标或被停止的plan ID。`RestorePlan`严格验证原请求标识、父ID、类型、批大小和成功/失败/停止/剩余计数，不能把停止项计为成功或失败。

复用生产`SecureFileCommandStore`与`PackFileJournal`，在受保护日志中新增独立版本化命名空间`restore_plans_v1`，仍按endpoint+serverId隔离。原`scopes`命令和其它字段完整保留；同一串行写队列检查普通文件命令及整份恢复的资源重叠，避免两个日志先各自放行。没有新建明文文件或把token/媒体字节放入任务记录。

首次POST前先落完整意图，写盘失败不发送。原任务ID只绑定同一不可变请求；未知响应、404、错误身份、坏计数均保留原记录。重新打开、再次遇到同一待核对意图只GET原回执，不重发POST。已验证的终态只结算同一请求；停止回执证明受理后只结算该停止命令，不清掉仍在执行的整份恢复记录。换连接或管理数据代次后旧网关失效，迟到结果不得发布到当前界面。

恢复与停止分开记录。停止即使从另一设备创建的服务端计划进入，也只需绑定明确的plan ID；不知道全部原成员也不能伪造选择。单个计划已有未确认停止时禁止再发新停止命令。

## 原回执协议补齐

父计划读取增加`request_id`以核对原请求。POST停止返回`stop_request_id`；GET `/api/v1/pack-restore-stop-requests/{request_id}`读取原停止回执，不新建、恢复或重新入队。任务轻量摘要增加`stopped`和`remaining`标量。此阶段尚未发布，App与包含这些协议的兼容服务端一起按依赖部署，不能只部署半套开发分支。

## 界面

沿用现有Paper、设置行和全高度任务详情，不另起视觉方向。整份恢复使用短确认面板，明确可离页及任务入口；回收站显示未确认恢复/停止和“查看恢复计划”，操作任务也能找到未拿到ID的本机原请求。原成员按24条真实分页，失败与已停止分别表达。

任务详情的“停止后续批次”再次确认，说明先核对当前已受理批次、只停止未开始内容、已恢复内容不回收。未知停止禁用再次提交，查询只查原停止ID；已停止成员标明“未执行恢复”，不在每行重复长错误解释。计划计数使用“失败”而非把25个停止项混进“未完成0”。

受理提示的SnackBar在进入二级任务详情前关闭，避免保留多个Scaffold时的Hero冲突；该问题由真实Android快速跳转发现，并有完整App回归覆盖。没有修改Flutter SDK或冻结HTML原型。

## 验证及后续

单元/HTTP测试覆盖1027项只提交一次、写盘失败、未知/404/坏身份、共享互斥、停止原回执、迟到结果及旧字段保留。Widget覆盖确认/取消、双倍字号、停止丢失、停止成员分页和仍有SnackBar时快速进详情。

Android测试使用真实`SecureCredentialStore`与`SecureFileCommandStore`（专用测试键），第一段在原恢复POST响应丢失且日志已经落盘后保持测试未结束，由宿主强停活进程并验证PID消失；服务端在App缺席期间恢复27包/14个唯一批次。第二段新进程不输入口令，从安全存储恢复原请求，只GET原回执，随后覆盖另一份计划停止响应丢失、原停止GET以及2包恢复/25包未执行。首段预期被中断不是测试通过，整轮必须以第二段实际通过且PID更换、文件哈希不变为准。正式固定源码的三轮原始证据另行归档。

永久删除仍每批精确清单与明确确认，其剩余选择持久化另需继续。v2管理备份与父/子/成员历史化、完整设置与默认值迁移、真机NAS、旧原生用例迁移及LF8所有原型状态仍待完成；不能据这一条强杀路径通过关闭整个LF6/LF7或总任务。没有发布APK或改动真实NAS。
