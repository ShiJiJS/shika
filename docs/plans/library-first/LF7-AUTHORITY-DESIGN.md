# 恢复后的管理代次与旧命令隔离

本阶段承接[备份v2完整设计](LF7-BACKUP-V2-DESIGN.md)与[只读历史](LF7-BACKUP-HISTORY-DESIGN.md)，先接实际服务端的写入隔离。它不是完整v2恢复、只读历史路由或App迁移的替代品；这些仍继续实施，`backup_v2`保持关闭。冻结原型独立未改。

## 协议和权限

`GET /api/v1/info`返回当前`management_epoch`和`management_authority`能力，登录成功也返回该次签发的代次。已鉴权响应的`X-Management-Epoch`在响应开始时读取已提交权威值，使客户端能发现同地址/同server_id的异机恢复。它是随机32位小写十六进制代次，不是身份凭据，不能代替Bearer鉴权。

新客户端每个网关/命令捕获不可变代次并发送`X-Management-Epoch`。请求头缺省时使用令牌的签发代次，让旧客户端也受保护；显式当前代次允许已核对新库的新客户端沿用同一个有效令牌，不要求保存口令或自动登录。错误/空/重复拼接的代次不作为缺省处理，严格422；旧代次写入409 `management_changed`，明确旧操作没有执行。只读原任务、回执、前快照下载仍可用原令牌查询。

自己撤销令牌与媒体代次独立；`DELETE /auth/session`仅撤销已鉴权的自身会话。原GET若内部会创建/修复播放范围或改变媒体元数据，也必须在实际写事务接受代次检查，不能用GET名义绕过。一般只读媒体库可继续读；App未来还必须在响应代次变化时失效旧读取的发布，不能把服务端写入拦截冒充完整界面隔离。

## 检查与提交

异步鉴权依赖把令牌身份/签发代次和该请求捕获的预期代次放进ContextVar，再由FastAPI复制给同步endpoint及run_in_threadpool。非GET/HEAD/OPTIONS先做一次短受理检查，避免旧上传走到任务受理；每次`Database.write()`在同一个RLock和SQLite `BEGIN IMMEDIATE`之后再检查，持有到提交。SQLite旧驱动的SELECT并不开始实际事务，只有RLock不足以约束另一数据库连接；显式写事务让代次检查与后续DML共用真正数据库写锁。

请求先持有写锁则先提交，再由恢复轮换；恢复先提交则旧请求在实际写库前拒绝。令牌在等待期间过期/被撤销也重新检查。上下文在请求结束时复原，不能泄漏到下一个请求。后台执行器不继承HTTP代次；受理恢复仍须先阻止/等待全部活动文件、扫描和管理任务，不能单凭此层检查宣称旧后台任务已隔离。

现有v1实际恢复在管理数据替换的同一个事务内生成新代次，并在进程故障检查点前flush；失败或提交前SIGKILL不能单独轮换。当前代次、令牌签发代次、凭据/server_id不从备份恢复或导出。v2逻辑管理表结构仍为0013，数据库0014仅增加不导出的令牌字段；完整v2恢复协调器后续复用这一事务规则，不能在恢复完成后另开事务补轮换。

## 迁移及兼容

0014只给access_tokens增加issued_epoch。旧令牌留空标记，首次鉴权初始化在同一事务中创建管理代次并绑定旧令牌；随后重启不改已有签发代次。已有签发记录但管理代次丢失/损坏时拒绝启动，不能静默生成新值再把旧令牌升级成当前。迁移沿用现有私有前快照和失败恢复机制。

旧客户端恢复后仍能读原回执，继续写需重新验证连接。当前App尚未接不可变网关代次、跨设备变化提示、真实安全日志和剩余选择历史化；本阶段只完成服务器部分，不声称该App现在能无口令自动恢复所有流程。新App接线时必须先持久标记旧命令/选择为历史，再用新网关读取当前库，不能只把ServerApi的可变header改成新值并重发旧命令。启动时saved token不等于saved命令属于当前代次，旧无代次日志必须保留为只读核对，不能自动提交。

完整待办仍包括：恢复预约/前快照/根映射与物理删除真相/完整替换/正式历史引用及孤立清理、所有导入任务历史不重放、任务协议和原回执路由适配、App有界传输与系统选择器、其余强停组合及LF8完整原型/真机NAS/签名升级。这里只在隔离数据和测试实例运行；不改正式8760、真实NAS、SDK或发布APK。

## 证据

实际HTTP检查代次缺省/显式、新旧令牌、异步导入、原任务GET、播放GET潜在写入、自己退出、令牌等待时撤销、受理后恢复/写锁内恢复两个交错及不同数据库连接。真实v1恢复和发布前快照、进程SIGKILL检查当前代次与原媒体/回执；升级/重启验证旧令牌只绑定一次。具体通过数量和原始日志在测试完成后归档；本文不代替运行证据。
