# 分目录扫描页面

跟踪[#139](https://github.com/ShiJiJS/video_viewer/issues/139)，依赖[#138](https://github.com/ShiJiJS/video_viewer/issues/138)，[草稿PR #148](https://github.com/ShiJiJS/video_viewer/pull/148)基于#147。实现源码`430fede546fe7649bdffeb7f399c6d86b6bbb212`。页面和指定目录请求已实现，普通安装包与真实服务的连续操作、NAS及手机检查仍待完成，票保持开放。

媒体库有扫描或需要检查的目录时，点“查看进度”一次进入媒体目录；平时沿用“设置→媒体目录”两次点击入口。活动进度直接展开，完成后可展开“查看扫描记录”。返回仍经设置回媒体库，不进入旧浏览页。

沿用当前Paper页面：一个主滚动区、最大420宽的进度区域、20内边距和14圆角，标题20、目录名15、状态与数字12–13。视频和图包分别分组，每个设置中接入的目录是一条明细；不为每个图包增加源目录卡。名称换行，同名目录才补来源路径。浅暗主题、320宽/两倍字体、844宽横屏保留相同比例，没有修改冻结参考原型。

明细同时显示阶段、对应单位的数字、问题与最近完成时间。A已完成1个图包/40张图片、B仍在读取63张时，A的结果保持。发现中的180张只写“已发现”，不作为最终分母或百分比。空源写“未发现图包”，没有可检查图片与图片数量未知分别说明。部分失败或读取中离线保留已核对数字；没有事实写暂无记录。缩略图待补充与内容无法读取分开，前者注明不影响入库。

媒体库提示、目录行和进度卡都读取同一个LibraryPreparation；进度轮询不重建媒体分页列表。网络断开保留上次事实并注明未同步；不自动重发写请求。旧服务的图包/视频汇总保留在所属类型下，明确缺少每个目录的图片进度，不拆分汇总来猜测。旧任务在服务重启后残留的“正在发现”条目随实际中断状态显示，带新任务ID的独立事实不受影响。

“全部扫描”只保留一个入口；支持两项能力root_scan_progress和scoped_scans时显示“扫描此目录”。指定请求只发一次root_id，不支持或被拒绝都不降级为全扫。请求失败在当前页面显示，排队和执行中禁用该目录按钮；完成A可以在B仍运行时排队重扫。连接已关闭后的旧响应不能对新连接启动轮询。

接页面时修正了服务队列的一个边界：运行中的全扫只有尚未完成的根能覆盖新的指定根请求；已经完成的A可以排队新尝试，重复请求再合并到排队A。新增真实路由/Scanner回归用例先在旧镜像失败，修正后检查A新增的第二张图片确实入库、B上次结果不变。仍是单工作线程，不增加并发负载。

[固定检查记录](evidence/lf8-root-scan-ui/README.md)包含客户端完整822项、23项新增检查连续三轮、分析，以及Linux完整478项服务检查通过。组件画面使用公开合成的V+A+B响应和Mac中文字体，在实际Flutter组件中渲染；不是普通APK操作，也不是NAS扫描数字或性能测试。界面假数据与真实服务用例分开记录。
