# 备份恢复完成后可立即继续操作

2026-11-01，处理 [#159](https://github.com/ShiJiJS/video_viewer/issues/159)，基于草稿 [#165](https://github.com/ShiJiJS/video_viewer/pull/165)。固定产品源码 `2de02374e21567d72cc8bb94dde0bda43fde5a06`，本机 runtime preview.8。普通原签名 preview.20/code26、客户端 `8416a3f7` 保持；无需新 APK。本轮未访问 NAS、未修改原型、API、数据库结构或图包回收/恢复逻辑。

## 问题与实现

这是管理数据备份恢复的问题。原失败发生于 cf9a 完整检查：恢复任务 completed、新管理代次和恢复前快照读取均成功，紧接着查看快照的 POST 却得到 503 / restore_in_progress。原日志继续保存在 [删除重试阶段](evidence/lf8-pack-purge-code26/full-server.log)，后续偶然全绿不作为修复证明。

原实现先在替换事务内发布完成记录、清除持久恢复标记，随后清理私有工作目录/历史，最后才释放内存里的恢复占用。现在由同一写锁保护“提交终态事务”和“释放该恢复的内存占用”，使下一条写请求看到的完成状态与实际许可一致。清理仍在提交之后；不会为了等待清理而把已提交的数据写成处理中，也不会提前放开尚未提交的替换。

成功和正常失败采用上述顺序；中断继续保留持久标记，由服务重开接续原任务。释放时核对原任务 ID，旧任务清理不能清除随后已受理的新恢复；旧任务清理异常也不能改写已提交的完成记录，或穿过新恢复的占用去写库。冷启动恢复尚未启动普通工作线程时，同样不能因旧清理结束而提前启动它们。

## 服务检查

新增 10 项确定性检查，覆盖 v1/v2 提交后成功、失败、提交前保护、中断/服务重开，以及冷恢复 A 清理期间受理 B、A 清理正常或异常结束时 B 的占用仍有效。旧产品四项均真实复现 503；修复后 10 项及完整 534 项通过，Ruff 与 150 文件格式通过。中间针对 50 项单列，不冒充最终源码的完整结果。

测试用故障服务的备份检查点改为临时文件写完再原子替换，避免观察者只看到路径存在却读到空 JSON；不改产品服务或文件操作测试工厂。现有 SIGKILL 恢复及管理权限检查包含在完整运行内。原日志保留 Starlette/httpx 兼容警告。

## 普通 App 在完成窗口立即操作

使用全新本机合成库，与上轮保留的故障目录、真实收藏和 NAS 隔离。3 张带行号的长图、1 个图包、原第 3 页 45% 位置及纵向偏好。准备阶段创建 S0（1 标签）和 S1（2 标签）的管理快照，进行一次准备恢复，使当前为 S0、恢复前快照为 S1。首次准备扫描因默认两秒稳定等待正常 deferred，明确提交第二次扫描；未重启服务、重新生成图片或重放恢复。

完整服务检查结束后才启动本轮自有 AVD，安装原签名普通 26，设备 APK 完整 SHA 匹配。App 查看 S1 快照、核对 /media 并明确恢复一次。私有测试检查点仅暂停提交后的清理，不改响应、数据库或许可逻辑。记录原任务 completed、持久标记为空、内存占用已释放；App 自己采用新管理代次、回到媒体库。

保持这个检查点暂停，重新进入“备份与恢复”，马上点“恢复前的快照”。真实原生 POST 得到 202，携带的代次摘要与提交记录一致；同一新校验任务显示 queued。原恢复记录及 finished_at 保持，原容器 healthy、RestartCount=0。解除暂停后，原队列自动完成校验并打开 S0（1 标签）预览；取消后当前仍为 S1（2 标签），没有第二次原生恢复。

App 既有逻辑会在管理代次变化后提交一次扫描，记录中单独列明；没有手动再扫来绕过故障。扫描更新索引/观察和两项扫描设置，恢复更新管理代次/历史设置；26 张其余业务表在恢复与自动扫描间保持，凭据保持。校验/取消期间仅原校验任务由排队变为完成，其他 34 张可见表、设置与凭据摘要保持。随后实际阅读会新增最近会话、更新阅读 revision/时间，不能称整库不变。

从“最近”打开原图包，原第 3 页实际图片接口 200、ROW13 中部画面对应 45%，两个标签/原偏好/页 ID 保留。源图片 3 份大小/SHA 全部保持，原导出及准备快照的归档字节保持。本轮没有文件永久删除或图包恢复 POST，也未重复测 App 强停；冷恢复与中断由上述服务测试证明，不能替代目标手机检查。
