# 扫描进度按接入目录独立记录，区分视频与图包

跟踪：[138](https://github.com/ShiJiJS/video_viewer/issues/138)。

来自用户“接入两个图包文件夹，应各自有进度”的反馈，继续 #24/#27/#32/#33。优先级：高。[进度页面#139](https://github.com/ShiJiJS/video_viewer/issues/139)依赖本票的数据契约。服务端实现及检查见[规则/边界](../LF8-ROOT-SCAN-DATA.md)与[草稿PR #147](https://github.com/ShiJiJS/video_viewer/pull/147)，客户端和NAS联调未完成，票保持开放。

原规划核对（code22/NAS当时快照）：`Scanner`是一轮Task、单工作线程，先视频再图包。`PackScanner`有整体packs.progress图片数/图包数，但每根目录条目只粗略计图包processed，discovered未正确填充，status也滞留discovering。NAS只读观察：图包整体已处理786张、11包，根条目却是discovering/discovered=0/processed=11；视频为598/598。现有root级数据不足，不能只改前端文字。

目标：每个“已接入的媒体目录”独立拥有扫描状态、数字、结果和最近完成时间；两个图包源目录A/B不合并成一条进度。这里的目录指设置里接入的根目录；其内每个图包是处理对象，不展开为几百张独立源目录卡片。

- [x] 明确轮次/目录/类型三层关联。目录状态覆盖排队、发现文件、读取图片/视频、核对、完成、部分失败、离线、停用、中断；一条目录完成后，后面的目录继续时保留其结果。
- [x] 分别记录视频文件数，以及图包的图包数/图片数；分清已发现、已检查、已入库、失败、等待稳定/跳过，单位和分母含义写入接口契约。边发现边处理时不假装已知最终总量。
- [x] 图包当前处理中的图片数字也归属对应目录，不等整包处理完才显示；失败/重扫/服务重启后不串用其它目录或旧轮次数字。
- [x] 一轮全部扫描保留，支持明确指定接入目录重扫。重扫A不重新核对B；重叠根按既有归属规则处理，排除停用/离线子树，身份与缺失保护保持。
- [x] 使用单工作线程/排队控制NAS负载，不为“独立进度”启动多个并发扫描器。重复提交有明确合并/排队语义，恢复不重放文件管理操作。
- [ ] 接口添加能力声明并保持旧客户端/旧服务兼容；不支持单目录扫描时前端不能悄悄退成全库重扫。

验收：视频根V+图包根A/B；A完成/B运行、A坏图/B可用、离线/停用、文件仍写入、部分处理后重启、轮次切换、只重扫A、重叠根归属；数字逐项对应实际输入，状态不出现处理11而已发现0或假100%。仅可丢弃夹具写入，真实NAS只读观察。

入口：`scanner.py`、`pack_scanner.py`、`library_state.py`、`app.py` scans接口及现有Task持久化。实施时确定数据落点与兼容迁移；不要先堆一个仅内存的前端百分比。
