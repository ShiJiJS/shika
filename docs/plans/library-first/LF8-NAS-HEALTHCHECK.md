## 修改原因与边界

旧探测每次启动 Python 并导入 urllib，Docker 整个进程只允许 3 秒，而内部 HTTP 等待允许 2 秒。前一轮曾连续 53 次超时；本轮只读预检又有连续 5 次 3 秒超时，容器重启 0、OOM=false。此时直接访问 /health 返回 200，但一次也花了 3.437 秒，所以不能把问题说成业务响应始终很快。

NAS 是原生 aarch64 / CPython 3.13，不是架构模拟。繁忙时，12 次旧命令的导入中位数 32.825 秒、最大 37.189 秒；HTTP 阶段还包括 urllib 的延迟初始化，并不等同纯服务端处理时间。放开 Docker 外层时这些进程最终均返回 200，不能据此说 Docker 自检通过。第一版使用 socket.py 的实验也不够：12 次只有 7 次满足内部总期限，未采用。

最终探测只导入 CPython 的 `_socket` 和 time，连接固定数字回环地址，避免 urllib、DNS、代理和文字编码等额外初始化。旧 NAS 上随后 12 次小探测均成功，导入中位数 0.011 秒、最大 0.983 秒；探测中位数 0.028 秒、最大 0.077 秒。这是先后采样，宿主负载没有同时受控；含 SSH/Docker 的执行耗时、导入耗时和 HTTP 耗时分别记录，不作为整个 App 的性能结论。

宿主曾有较高负载、脏页/写回和一个 D 状态 Python 进程；后续未抓到对应阻塞点，压力接口也不可用。文件与调度开销是观测结果，底层磁盘或宿主压力的具体原因仍未确认。

## 实际探测行为

- Docker 使用 `python -I -S -B /app/video_viewer/healthcheck.py`；不导入应用，不读数据库，不创建字节码。`_socket` 是当前固定 CPython 镜像的接口，未声称支持其他 Python 实现。
- 从连接、发送到收齐响应头共用 **2 秒**期限；只认 HTTP/1.0 或 1.1 的精确 200。响应头最多 8192 字节，不接受不完整头、跳转、其他状态码或慢速滴流。
- Docker 每 15 秒启动一次检查；整个探测进程预算为 **10 秒**，包含进程启动、文件读取和调度。HTTP 期限仍是 2 秒，未调整业务接口超时。启动宽限仍是 20 秒。
- 健康检查不负责重启容器。等待工具的观察窗口到期时继续跟踪同一容器，不凭等待超时重新启动服务。

13 项真实 TCP 测试覆盖成功、异常状态、分段响应、头不完整/过长、无响应/慢速滴流及服务未启动。完整服务端 **491 项通过**，代码与格式检查通过；保留原有一条 Starlette/httpx 弃用警告。

另外在实际 ARM64 runtime 镜像、只读根文件系统、非 root 用户和禁网环境中，执行 Docker 自身配置的探测命令，得到 **200 健康 → 503 不健康 → 200 恢复健康**。延迟 3 秒的响应以失败退出，含本机 docker exec 约 2.056 秒，证明外层 10 秒没有放宽 HTTP 期限。
