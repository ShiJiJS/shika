# LF6 App 图包永久删除

沿用冻结 P2 的设置→回收站→图包入口。用户先选择整包，核对准确图片范围，再明确确认永久删除；普通移除仍在媒体库/阅读器完成。图包与视频的标签、选择和回收操作继续独立。原型目录 `design/reference/library-first` 不改动。

原型差异：冻结页用“删除整包目录及其中所有图片”描述范围；依据既定 DEL-05，实际执行只删除确认清单中的索引图片，保留附件，仅清理身份一致的空目录，因此 App 明确写出保留附件并提供图片清单。冻结文件保留为设计基线，这处语义差异记录在此，不能将它描述为逐字一致。

## 流程与比例

复用 Paper 的字号、配色、按钮和 SheetFrame，不增加新的导航层级。选择栏并列“永久删除”和“恢复”；大字号时数量独立一行，动作自然换行。弹层标题21、边距20，正文随系统字号，不靠缩字容纳内容。

选择→后台准备精确清单→显示包数/图片数/大小/附件保留说明→可分页查看图包和图片→勾选不可恢复声明→“确认永久删除”→原请求进度/结果。取消或关闭准备弹层不会提交文件命令，重新打开需要重新勾选。清单过期、摘要变化、连接/管理数据代次变化都会使确认失效。返回回收站继续保留未完成选择。

这是对误删的防错：用户可以直接检查将删除的图片，不需要自己根据图包数量猜测范围。代价是永久删除多一次清单核对，普通快速整理的操作数不增加。承载、反馈与原回收站相同；没有新视觉方向或候选方案。

复用三处反馈：240ms弹层进出、准备/查询时的进度条、勾选后的确认按钮状态变化。结果与错误按实际范围呈现；空结果缩短弹层，有明细时使用限定高度的虚拟列表，外层支持窄屏和大字号滚动。

## 清单和命令边界

PackPurgeGateway 固定服务连接与数据代次，承担只读准备回执、逐包图片分页和逐步骤结果分页。DTO核对清单成员、摘要、汇总、图片路径与分页完整性。准备响应丢失时 GET 同一请求；查询原清单不重发 POST。准备没有文件副作用，当前准备弹层不作为全局持久化任务中心。

ReviewSession 只生成不可变命令，不提交删除。明确确认之后，既有 PackFiles/受保护命令日志先保存 request_id、plan_id、digest、trash IDs 与确认图片数，再发严格 confirmed=true 的命令。迟到回执只能应用于原连接。结果成员和总图片数必须与本机确认范围一致。

未知删除响应保留原命令；重开待核对入口只 GET 原回执，404也不自动提交。用户明确重提时仍使用原键和负载。已受理的任务用原ID查询。查询/离页不停止服务端已受理操作，也不触发后续未提交批次。

每份清单最多1000包。超过时只准备所选快照的第一批，每批需重新核对确认。LF7现已持久保存完整选择及未提交剩余范围，并在回收站和任务入口可找回，详见 [后续设计](LF7-PURGE-SELECTION-DESIGN.md)。这份选择不是删除授权，永久删除不自动执行未核对批次；早期每批日志与最新完整选择分别记证。

## 部分结果和恢复

永久删除结果分别显示确认已删除图片数、未完成包数、待核对图片数；逐项结果支持“未完成/全部”和分页，显示包名/相对图片路径。附件与不可清理的目录保留不算失败。

部分完成条目显示“已有N张永久删除，恢复仅限剩余M张”，通过服务端 latest permanent operation ID 重新打开原结果。操作结果已知且没有待核对冲突时可清理对应命令记录；有 needs_attention 时保留原记录和资源互斥，不将未知结果计作成功。

“重试原任务”另行确认，使用原操作ID/原清单，只重试未完成内容。重试命令与其已知原任务共享资源；其它新删除/恢复命令仍被未核对资源阻止。确认安全结算后只清理已经绑定同一任务ID的日志，不误删尚未确认身份的请求。
