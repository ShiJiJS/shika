# LF7 统一操作任务

意图：按冻结 P2 接入已有任务与错误恢复，不重新探索视觉方向。用户想离开原页面后找到操作的真实结果，能判断完成、部分完成或仍待核对，且查询不会再次删除或恢复内容。

## 当前实现的边界

设置“数据维护”下增加“操作任务”，沿用原来的15px设置行、Paper颜色/字号和完整管理页。列表按24条从真实服务分页，按类型与状态筛选；本机尚未结算的请求单独置顶，已知任务ID与本页服务端记录去重。待核对来源也遵守类型/待处理筛选；不把本机请求计作已完成服务端任务。

列表与逐项明细都使用全高度页和虚拟列表。详情显示业务标题、实际状态、可核对的数量和任务编号，失败/历史明确区分。两倍字号分页自然换行，不缩字；失效连接/数据代次隐藏旧页并要求重新打开。弹层沿用240ms进出、ChoiceChip选择反馈、读取进度条；本阶段不更换设计系统。

原先扫描、视频、图包和管理恢复的结果散落在各页面，设置没有统一入口。现在从设置进入任务、选择记录就能看到原结果；本机未拿到任务ID的请求先查询各自原回执再进入详情。原数据读取失败保留已有同查询内容，不把错误显示成空列表；本机回执读取与服务端历史读取互不掩盖。

## 模块与只读契约

`MaintenanceTasks`提供只读的轻量摘要和成员分页。`/api/v1/tasks`旧接口保持兼容；新接口只投影任务标识、类型、状态、时间、历史标记和标量计数，不为列表物化每个Task.result的全部文件或备份清单。分页数量与成员读取短时间串行，以免工作器更新产生计数/页面撕裂。稳定顺序为创建时间与ID降序。

| 接口 | 行为 |
| --- | --- |
| GET `/api/v1/maintenance-tasks?offset&limit&family&state` | 最多100条摘要，默认24；视频/图包/同步/备份类型，进行中/待处理/完成/历史筛选 |
| GET `/api/v1/maintenance-tasks/{id}` | 同一任务的当前摘要；缺失404，不新建 |
| GET `/api/v1/maintenance-tasks/{id}/items?offset&limit&unfinished` | 包/视频操作成员分页，验证operation ID；不载入图片清单或复制所有结果 |

处理中、部分完成、需要核对、失败、中断、历史是不同状态。永久删除的已归档页和待核对页分别显示，已删除页不足不能冒充全部完成。无法证明文件结果完整时显示待核对；扫描有不可用/失败目录时显示部分完成。历史操作只读，不开放原操作重试。未知类型保留可查询记录，不据其内部kind推断业务成功。

`MaintenanceTaskCatalog`隐藏服务分页、取消、连接与数据代次、三种本机回执和备份下载。页面不调用HTTP/NAS。任务列表始终GET，详情查询仍GET；重新打开不调用提交方法。网关只受理自己发出的回执对象，并核对原request ID、任务ID与类型，不能把另一个请求的结果当作自己的。

## 原回执结算

- 图包使用既有PackFiles协议校验成员/数量，GET原文件或重试回执；明确完成且没有needs_attention时才结算日志，部分或失败保留可见结果。待核对冲突继续保留日志/互斥；历史回执只归档本机同一请求，不执行旧操作。
- 视频使用既有原文件回执，并按预期request key进行本机结算；排队期间若已换成另一个命令，旧查询不能代替它查询或清除新命令。
- 备份导出/校验/恢复分别读各自原回执。已找到的任务ID保存回原日志，之后仍用同一任务；恢复完成后走原权威状态同步和数据代次失效路径。旧key的绑定/确认不能清掉新导出或恢复。
- 404不重新提交，也不伪造成功；保留原请求供核对当前内容。历史归档只清本机已识别的旧请求，未知请求不丢。

图包永久删除详情复用既有逐图片结果与明确原任务重试；查看不提交，重试需要另一次明确动作，仍使用原清单/原操作。已经删除的内容不恢复。

## 原备份下载

详情“下载原备份”从选中的已完成backup_export读取原artifact，校验原SHA和UTF-8，最多32MiB。没有新的导出POST。取消保存、下载失败或校验失败保留原回执；保存成功后只清理指向同一任务的本机导出记录。文件选择/保存继续通过原BackupFiles适配，不把本机路径/凭据写入任务数据。

## 整份批次计划：仍必须继续

当前统一入口接的是服务端任务和现有每批请求日志，**还不是整份多批次计划**。旧恢复界面离页停止后续未提交批次、关闭App不保留整份选择的问题仍存在，不能据本页面已完成而关闭DEL-04/06或LF6。

后续整份逻辑恢复须持久化不可变成员、父计划与唯一子批次，复用包级互斥；一次明确授权整份选择后，由服务端持续推进有界批次。App离页/关闭只影响读取，重开只GET原父计划，不重新发整份恢复。已知失败逐项保留；中断先核对原子批次，再推进下一批；停止后续批次保留当前实际结果，不能清掉未知操作。管理恢复要对父计划、子任务、成员与回执一并历史化，旧计划不能执行。

物理永久删除继续每批单独核对精确清单和明确确认，不能借批次续作自动删除尚未核对的下一批。剩余选择/计划也须持久化并在任务入口可找回；与逻辑恢复的授权范围分别表达。

## 验收

服务端要验证摘要不物化8万条大型结果、类型/状态/稳定分页、历史/待核对和权限；客户端要覆盖原请求只GET、未知/损坏/迟到结果、陈旧key不能影响新请求、下载校验与取消保存。真实Android从设置走任务分页、原回执恢复、历史记录及原备份下载，文件哈希和请求轨迹独立记录。当前生产备份仍为受保护的v1，真实图包数据会明确要求v2；不把旧导出下载作为图包v2往返通过证据。

完整设置逐项对照、备份v2/v1转换、默认值迁移、整份批次、真实安全存储强杀、原型全状态/暗色横屏与真机/NAS仍待后续。冻结原型目录不变，仍独立可移除。
