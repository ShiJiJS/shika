# LF5 图片失败后的末尾导航

承接 PR #55，解决 PKG-03、READ-01/02/04/05 的一个实际差距。冻结原型 `runtime/reader-base.js` 的 `advance(1)` 在最后一张打开 finished；原 App 将“跳过这一张”目标截成最后一张，横向停在失败页，纵向也没有明确切到可操作的末尾状态。底部“下一张”原来在末张禁用，与该原型路径不一致。

## 行为与归属

页内跳转仍使用已有阅读 session 和固定图包范围。仅在当前已是最后一张、明确请求越过末张时，路由进入现有 `_PackEnd`；不新增阅读会话，不改候选，不自动下一包，不创建图片管理对象。

末尾是一个导航状态，不作为图片已解码或已阅读的证据。失败图片没有首帧，因此不能写 opened、最近、进度或 completed。“返回最后一张”回到原页；“返回来源”沿用退出时的 flush/未知结果处理；只有点击“阅读下一包”才切换原范围中的下一个包。沉浸中触发末尾时显示工具，避免有明确名称的返回动作先被当作退出沉浸而吞掉。滑动到原有末尾页的逻辑保留。

模式切换、明确页码跳转、换包和快速整理推进均清除末尾导航状态。管理代次/连接失效继续由已有 session 拒绝并隐藏旧内容。沿用现有 Paper 页面与末尾按钮；黑色画布上的返回动作使用既有图片失败动作的白色，修正原先低对比度。

## 检查与证据边界

真实本机 HTTP 404 与 HTTP 200 非图片字节经过生产 NetworkImage/解码路径；组件检查普通、双倍字号和横屏，横向/纵向跳过、返回末张再点击下一张、沉浸与原来源保持。服务端阅读元数据在组件层使用已有 adapter，不能据此宣称完整 HTTP 阅读流程。

独立8764夹具每轮使用新目录和新数据库，实际生成两包共6张合成 PNG；仅对属于异常包的原图 GET 替换404或损坏响应，缩略图和正常包仍走真实读取。原生完整 App 从媒体库进入原固定范围，失败末张到末尾不写阅读，手动下一包显示真实首帧后才记录最近；API断言与独立SQLite核对分别保留。使用现有 AVD、`--no-uninstall`，不清应用数据或更新SDK；测试不作为安全存储强停、目标手机/NAS或所有图片错误码的证明。

本次不重开 UI 设计方向，不改冻结原型。其它图片错误码、连接/恢复/迟到图片、500页4K/8K性能、全原型与目标环境仍有独立验收范围；本段完成也不能关闭 LF5/LF8 或总任务。
