## 实际流程

从四入口App进入设置→备份与恢复，实际查看浅／暗色页面。导出经HTTP任务生成并流式下载到Android私有文件，真实DocumentsUI保存框中手动改为唯一名字，再点SAVE。按本轮Download新增文件精确识别，用ADB文件传输取得副本并核对大小／SHA；重新选取时严格要求UI中只有一个同名条目。生产建议名仍是video-viewer-backup.vvbackup，改名是系统界面的实际输入动作。成功后导出的文档留在专用模拟器供复核，工作目录也有同字节副本；其它文件名集合不变。

真正选入后，生产原生桥接复制所选content URI并执行协商上限及摘要校验；App／HTTP上传同一字节文件。恢复表单27根按24＋3分页，真实键盘可打开／关闭，确认默认未勾选。明确勾选后只提交一次完整替换；导出后新增的两类标签被移除，连接自动转入新管理代次，原恢复任务完成，恢复前快照可读。快照再次预览时确认仍关闭、按钮禁用，没有第二次恢复。

两轮各只有一次导出POST、一次文件导入POST、一次完整恢复POST、一次初始登录与一次指定快照预览。真实安全日志分别在系统保存前、恢复确认前和恢复／快照后读回，记录原请求／任务／文件标量；其请求键与HTTP的request_id／Idempotency-Key一致，最终原恢复记录settled=true。保存的安全日志均小于64KiB，没有将19KiB／41MB文件放入安全存储；这不是Android总内存峰值测量。

## 取消仍保留原工作

大文件先在真实系统保存框按返回，生产桥接返回false，页面显示“保存已取消，原导出任务已保留”；安全日志完整对象与进入系统保存前相同。之后明确再次导出，复用同一原请求／任务／私有文件，不新增导出POST。实际保存后第一次系统选取再次按返回，返回null、没有恢复表单，安全日志不变。两个取消检查点的请求轨迹均没有导入或恢复POST；随后明确重新选取唯一新文件才完成实际恢复。不是以旧SAF边界检查和私有适配器取消结果拼接成整路结论。

## 数据核对与大文件边界

大文件由18,000条已完成的测试操作记录（每条2048字符备注）真实生成，未扩张媒体文件。恢复前后按ID排序的操作ID／类型／状态／阶段／备注摘要完全相同，实际导出文件中也逐条解析核对。小文件／大文件都从容器结束后的只读SQLite查询取得目录、两类标签、图包与页投影，并与实际导出文件比较：27根、各1个标签、1包1页、ID／类型／启停／路径／页信息相同。图包content_version由1到2是既有backup_restore_graph.py的max(imported,current)+1规则，作为明确期望核对，没有把它说成全库字节相同或去掉版本字段来强行通过。恢复任务historical_operations_replayed=0，两份媒体源文件大小／SHA前后相同。

实际Android保存／读取／上传的是未压缩40,964,503字节文件，超过旧32MiB；测试服务明确协商64MiB。Git中的exported-document.vvbackup.gz仅为减小证据体积，解压后的大小／SHA必须与Dart、系统文档和HTTP输入标量一致。没有生产默认改成64MiB，没有目标手机、云文档提供器、全App／服务端全集、断网／损坏／超限全部组合或发布验收结论。既有独立40MiB和服务端分配峰值证据不混作本轮峰值。
