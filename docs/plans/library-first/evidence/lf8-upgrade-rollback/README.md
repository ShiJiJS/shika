## 发现并修正的实际问题（#93）

最初cf992025演练中，旧视频回收任务的原状态为completed、成功1/失败0，持久成员已完成；新任务列表却显示“结果待核对”。当前FileOperations.finish同样省略total/processed，因此当前新建的视频任务也会误判。修正增加新回执计数，旧记录则由只读查询核对原operation_id、结束状态、旧格式和持久成员数，补足可确信的汇总；不改原JSON、不执行原命令。

## 最终三轮：accepted-1 / accepted-2 / accepted-3

三轮使用**同一公开样本**，同一个最终QEMU进程，正常App六次冷启；每次新PID不同。每轮均完成：

1. 用停止后的0004基线正常启动新镜像，由生产Database.migrate执行到0014；自动迁移前快照的全部旧表投影与基线相同，原token旧列投影相同，并绑定到当前管理代次。
2. 原标签、关联、播放轮次/成员、请求记录、文件操作/成员和回收站逐表相同；原视频/根目录/目录身份和其它原字段保留。扫描仅更新根last_scan、可用视频及目录seen_scan；增加扫描任务和management_epoch/playback_defaults设置，完整差异有原始投影可核对。
3. 正常APK免口令进入新媒体库，1视频/0图包；启动窗口全GET，无自动stream/opened。标签、回收站和原任务可读，旧任务显示“已完成”，全部成员1项已完成。打开这些入口的前后原列投影相同。
4. UI明确创建AFTER_UPGRADE_FINAL_n标签，每轮唯一一次App写请求为POST /tags。然后强停App，以独立控制凭据只读核对真实HTTP原回执，撤销该临时凭据，原token表摘要恢复相同。
5. 停止并移除新容器，完整保留升级后副本；在原数据绑定目录内恢复全部基线内容，保留目录/数据库文件身份。宿主文件摘要、schema0004及全部旧表投影匹配；**旧镜像内实际SQLite读取**再次检查版本、完整性、文件SHA，确认与宿主一致后才启动旧服务。
6. 正常APK新PID免口令回到兼容旧视频界面。原可用视频、标签、回收站保留，升级后标签消失；App只GET、未向旧服务请求图包API。独立控制窗口再GET原文件请求，回复与基线原回执完全相同；控制凭据撤销，原token不变。
7. 停止旧App/服务，保存回退后副本和每轮结果，原媒体SHA相同；下一轮从相同停止基线完整重新开始。

`accepted-n-result.json`记录各轮成功；`accepted-n-new/`及`old/`记录schema、投影、镜像、原回执、界面事实与停止结果，`accepted-n-restore.json`记录完整恢复。每次服务启动前有`container-preflight.json`。`trace/`只记录时间/方法/不含查询串的路径/状态，没有认证头或请求体；`observe/`保留实际uvicorn路径日志格式器，无响应改写或服务源码绑定。

App窗口由实际冷启偏移与保存的请求切片界定；`host-http-inspection.json`另外记录控制窗口的起止偏移、临时登录和撤销。整份trace包含这些明确的控制登录，**免口令声明只针对App窗口**，不把控制登录掩成零登录。
