# 图包按文件夹后台删除

对应[#186](https://github.com/ShiJiJS/video_viewer/issues/186)和[#188](https://github.com/ShiJiJS/video_viewer/issues/188)。用户明确纠正此前的图片核对方案：图包以目录为单位，选中后点击永久删除，服务器后台移除整个文件夹，不等待逐图清单。

## 最终操作

图包移入回收站仍只记状态、保留源文件。回收站选择图包后点“永久删除”，直接把选定目录提交到服务器；不创建图片准备清单、不计算图片散列、不展示清单或勾选框、不等待实际删除完成。目录中的图片、附件、隐藏文件和子目录一并删除。符号链接只删除链接，不跟随到外部目标。

App在内部持久化原请求后异步发送。大选择按1000项自动分批，页面可以立即离开。正常流程按视频的方式处理：媒体库移入回收站直接执行，显示短提示和撤销；撤销也不弹提交进度。永久删除不创建“保存的删除选择”，不展示待核对、提交记录、清单与进度弹窗。请求已受理后从列表隐藏处理中目录；后台完成后自动清理本机未完成状态、刷新列表和数量。重新打开App也会查询旧请求并自动处理完成结果。网络丢失响应时只查询原请求，不自动重复提交；失败目录保留，可以重新选择重试。任务历史仅作主动查看，不是正常操作步骤。旧的图片删除命令、历史任务和旧服务接口保留兼容；新NAS服务开启目录删除并停用旧图片清单准备入口。

## 服务端

`POST /api/v1/pack-trash/directories/permanent`，参数为`request_id`、`trash_ids`和`confirmed:true`。接收事务只读取图包/根目录标识、回收状态、路径和目录身份，批量写入现有`pack_file_operations`和`pack_file_steps`，立即返回202；不读取回收记录的图片manifest或`pack_pages`。任务类型为`pack_directory_delete`，复用原操作编号回执、后台队列、重启恢复和重试接口，不增加数据库表或迁移。

后台按目录处理：确认仍是所选回收记录及已配置根目录内的文件夹，按目录设备/节点身份移到同父目录下的服务临时位置，再用不跟随符号链接的递归目录删除。不会逐张读取图片内容或计算指纹。目标路径替换、授权范围改变、嵌套配置目录、并发恢复/其他操作均拒绝误删；中断后只恢复同一目录身份，原位置新出现的文件夹保留。已完成目录不重复删除，失败目录继续保留回执与原任务入口。

旧图片准备任务不是删除授权。部署设置`VV_LEGACY_PURGE_PREVIEWS=false`：旧的未完成只读准备不再重启散列，保留中断记录；旧准备POST返回升级提示。已确认的旧永久删除命令继续使用原执行逻辑，不转换为目录删除。

## 部署与验证

App第34版`0.2.0-preview.28+34`，服务`0.2.0-preview.9`。图包挂载`/packs-cos`由只读改为可写，其他挂载、用户、端口、口令与资源限制保持。升级前保存完整停机数据/配置/Compose/口令文件及旧镜像，保留用户要求的私人回收站记录；不对真实收藏执行删除试验。

隔离测试覆盖整个目录/附件/新增文件、外部链接、622项接收不读图片字段、请求去重、替换目录、中断后续删及保留新原路径、管理备份格式和旧清单停用。客户端覆盖无清单弹窗、网络未返回时退出、多批请求先持久化、丢失响应只GET原回执，以及任务/回收站/选择历史兼容。服务器部署检查见[第33版说明](../../nas-app-preview-2026-11-03-code33.md)，当前App交付见[第34版说明](../../nas-app-preview-2026-11-03-code34.md)。不恢复其他暂停的持续开发与旧验收。
