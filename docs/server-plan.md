# 服务端技术方案与联调计划

2026-10-16 用户已确认下列技术栈，并要求同步文档和后续任务。服务端已进入实现，逐项完成情况与证据见 [服务端验证记录](server-validation.md)。环境实测见 [WSL2 Docker 开发记录](server-development.md)，业务范围以 [第一版规格](v1-spec.md) 为准。

## 已确认技术栈

| 部分 | 选择 | 职责 |
| --- | --- | --- |
| HTTP 服务 | Python、FastAPI、Uvicorn、Pydantic | 认证、请求校验、业务 API、OpenAPI 文档、缩略图和授权媒体入口 |
| 管理数据 | SQLite、SQLAlchemy、Alembic | 标签关联、目录和视频身份、轮次、任务与文件操作记录；事务及数据库迁移 |
| 媒体工具 | FFmpeg、ffprobe | 提取时长、尺寸、旋转和编码信息，生成可再生缩略图 |
| 后台任务 | 服务内受控任务执行器，任务状态持久化到数据库 | 定期/手动扫描、媒体探测、缩略图、备份和恢复；限制并发，启动时核对未完成任务 |
| 部署 | Docker Compose，单服务、单端口 | 在 WSL2 开发，在 NAS 部署；依赖随服务镜像安装 |
| 服务端验证 | pytest、HTTPX | 通过公开 API、真实隔离媒体目录和测试数据库验证行为 |
| 客户端验证 | Flutter integration_test、Android 模拟器 | 验证真实网络链路及已确认的播放、管理和恢复交互 |

FastAPI 的参数校验和接口文档用于明确 Flutter 网络契约。SQLite 适合当前个人单实例服务，数据库由服务端在本地持久数据卷中读写；开发环境使用 WSL 原生目录或 Docker volume，NAS 部署使用 NAS 本地文件系统。视频目录独立挂载，客户端统一通过 API 访问。

依赖版本、镜像基础版本及 SQLite 运行时版本在 S1 实施时核对并锁定。正式 NAS 的 CPU 架构与可用资源尚未提供，发布镜像的目标架构在取得设备信息后验证。

## 运行与接口边界

- 单个应用提供认证、JSON API、缩略图及媒体读取。第一版采用单实例，后台任务在数据库保留状态；限制探测、缩略图和内容校验的并发，阻塞磁盘操作及媒体子进程通过受控执行器处理。
- 原视频优先直接提供授权流，支持 HTTP Range、长度与类型信息、取消读取及可解释错误。解码、倍速和临时长按加速由客户端播放器负责。兼容转码在真实样本验证后另行评估。
- S1 明确 API 版本、稳定目录/视频标识、分页、可用性、错误结构和任务状态；S3 补齐稳定标签标识。客户端行为契约见 [客户端数据边界](client-data-contract.md)。
- 长任务提供可查询的任务标识和结果。写操作按需使用请求幂等标识、操作标识和逐项结果，断线重连后可核对实际状态。
- 删除、恢复和永久删除由统一文件操作边界处理，持久记录意图与阶段，重启后核对文件和数据库；真实文件与数据库各自的提交需要故障恢复机制。
- 暗黑模式、控件显隐、窗口亮度和设备音量由客户端管理；外观偏好继续保存在本机，不进入 NAS 管理数据备份。

每张 S 任务以公开 API、真实临时文件及数据库结果验收；I 任务再以模拟器中的公开 UI 跑真实服务链路。V1 汇总完整回归并验证 NAS、目标手机和实际媒体样本。GitHub 原有任务与原生阻塞关系继续使用，环境探针和客户端演示不代替业务完成证据。

I1 将演示数据层的同步列表与目录查询演进为异步分页加载，并处理加载、空态、失败、重试与过期响应。I6 将同步备份字符串处理接到真实异步导出/传输/校验/恢复任务。原有已确认交互继续保留，演示提供方与真实提供方遵守同一行为语义。

I2 补齐最新反馈的网络回归：纵向跟手切换与回弹、仅当前视频发声、长按临时 2 倍速及取消恢复、画面和底部横向拖进度、悬浮名称/标签、控件自动隐藏、横屏返回/亮度/音量。暗黑两个入口同步和本地持久化也在联网后的 V1 回归中验证。

## NAS 资源与预加载

用户提出希望根据 NAS 能力评估预加载能否让短视频切换更顺畅。先保留为待实测事项：预加载能否获益、可预加载多少、流量和内存代价，都需用实际视频、NAS 和网络比较。

基础实现要求：

- 当前播放和前台管理请求优先，后台扫描、缩略图和内容校验使用受控并发、超时及可调整的资源参数；媒体流按需读取，及时停止已取消的读取。
- I2 验证现有相邻播放器预初始化在网络模式下的资源边界、静音和释放行为。预加载范围应有限且可停用；切换目录/筛选/轮次、删除视频、凭据失效及退到后台时清理不再需要的请求和播放器。预加载不推进轮次，也不改变筛选结果。
- 不把演示素材的流畅程度作为 NAS 性能结论。V1 记录 NAS CPU 架构、内存、存储和网络条件，以及样本数量、时长、编码、码率和分辨率。

可选优化研究已记入 [后续事项](backlog.md#nas-能力与短视频预加载优化)：优先比较关闭预加载与仅准备下一条的有限缓冲/首帧，不扩大成整库下载。对比首帧和切换延迟、卡顿、NAS CPU/内存/磁盘读取、网络流量及客户端资源占用，再决定预加载窗口、缓冲大小和是否需要更复杂策略。测试素材要覆盖连续快刷、回看、拖进度和长按倍速场景。

更大的缓存、自适应预取或其他性能优化以实测收益决定，当前不作为 S1–S6 或 I1–I6 功能验收的新增阻塞项。V1 仍须完成原本约定的真实目标性能测量，阈值在取得实际样本和设备条件后约定。
